# Task 3 — Recovery, Forensics, and User Problem Validation

## Objective

Define a safe recovery workflow that preserves source data and communicates the limits of deleted-file recovery.

## Scope

- Separate forensic acquisition from recovery output.
- Require a different destination for recovered files and images.
- Define write-blocking and read-only expectations.
- Define hashing, working-copy creation, acquisition metadata, and chain-of-custody fields.
- Document SSD/TRIM limitations and recovery uncertainty.
- Compare OSCP’s intended workflow with DBAN, Blancco, and established forensic tooling.

## Deliverables

- Recovery workflow specification.
- Source/destination validation rules.
- Acquisition and recovery result model.
- User-facing warnings for SSDs, encrypted volumes, damaged devices, and live system disks.
- Research notes and references in `docs/recovery-research.md`.

## Acceptance criteria

- Recovery never writes recovered output to the source by default.
- The workflow distinguishes “not found” from “not recoverable.”
- Every acquisition records source identity, destination, tool version, timestamps, errors, and hashes when available.
- The application recommends WinPE or hardware/software write blocking when normal Windows access could alter evidence.
- The product does not promise recovery from SSDs affected by TRIM.

## Dependencies

- Read-only helper behavior from Task 2.
- Audit events from Task 4.
