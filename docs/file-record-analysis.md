# Read-only FAT32 file-record inventory

The candidate inventory reads the root directory of a validated FAT32 volume in an already selected regular raw image. It lists 8.3 short-name entries with their on-image record offsets, allocated/deleted markers, file/directory attributes, stored file sizes and first-cluster metadata. It does not read candidate file contents or reconstruct file chains, recover files, scan subdirectories, reconstruct long names, interpret NTFS/exFAT file records, or modify the image. All candidates are explicitly `metadata-only`.

`inventoryFat32Root(read, sizeBytes, partition)` accepts a bounded reader supplied by the trusted regular-image service. That service must retain the selected read-only file handle and check its identity before and after reads; caller-provided raw paths are not part of this API. The inventory re-reads FAT32 boot geometry, follows only the root-directory FAT chain, honors active-FAT flags and checks mirrored root-chain entries. Cycles, free/bad/reserved/out-of-volume chain values and inspection limits produce partial results with warnings. Invalid boot geometry and unsupported filesystems cannot claim candidates.

The limits are 1024 candidates, 128 root clusters, 4 MiB of directory entries and 8 MiB total metadata read budget, with each read at most 1 MiB. End-of-directory markers terminate the scoped inventory. This is a bounded root inventory, not a complete deleted-file search. An empty result does not mean `NotRecoverable` or prove that no deleted data exists.

FAT directory markers describe directory-slot state. A deleted/free marker does not preserve the original first name byte or prove the remaining fields describe a recoverable file. Names needing an unknown OEM code page are displayed with `?`; long-name slots are skipped. First-cluster numbers and sizes are stored metadata, not verified content ownership or an extraction plan. A deleted candidate can refer to overwritten, reallocated or unavailable content; no recovery percentage or successful recovery is inferred.

This milestone uses the [Microsoft FAT specification](https://www.scs.stanford.edu/~zyedidia/docs/_other/fat.pdf), including its directory-entry and FAT32 allocation semantics. The original Microsoft FAT specification is also identified in the [UEFI Forum's related documents](https://uefi.org/uefi). Microsoft's [FastFAT driver source](https://github.com/microsoft/Windows-driver-samples/blob/main/filesys/fastfat/fat.h) independently documents corresponding directory-field offsets. The implementation reads these structures; it neither mounts the filesystem nor executes boot code.

The tests include valid/deleted records, root-chain cycles and corruption, mirrored/active FAT selection, inspection caps, unsupported filesystems, malformed input, source-reader failures and a disposable regular-image fixture opened read-only. The real-file test verifies unchanged image SHA-256 and modification time. These checks do not certify behavior on every damaged filesystem or constitute successful deleted-file recovery.
