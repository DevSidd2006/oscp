# Recovery provider boundaries and demo fixtures

`RecoveryWorkflowProvider` is the common UI-facing port for capabilities, source listing, analysis, acquisition/recovery requests and shutdown. Requests accept opaque source/record IDs, never physical paths, arbitrary byte ranges or renderer-provided output paths. Each adapter owns target resolution, source handles, output selection, identity checks, cancellation, validation and audit recording. Result provenance and simulation flags must remain visible in the UI.

The demo adapter creates private 64 KiB regular-file fixtures with illustrative NTFS/exFAT boot geometry. Its allocated/deleted record examples are predefined synthetic maps, not parsed NTFS/exFAT file records. Acquisition copies a fixture file; recovery simulation copies a known mapped payload. Every source, analysis, sidecar and audit event is explicitly labeled demo. `physicalAcquisitionPerformed` and `recoveryPerformed` remain false even when synthetic deleted-record bytes are successfully copied. This does not prove support for real NTFS/exFAT recovery.

Sources are held read-only during operations. Visible/held identity is checked around bounded reads, the complete fixture digest is checked afterward, and output is independently reread for SHA-256 comparison. New output and sidecar files use exclusive creation. Outputs cannot share the fixture source directory or an audit directory. Directory separation in a demo is not physical-device independence. Sources are retained unchanged; the provider does not remove them on shutdown. Cancellation/failure retains created partial outputs with explicit status.

`selectRecoveryWorkflowProvider` selects demo only on explicit demo mode. Production defaults to an unavailable adapter and never falls back to demo. An explicitly configured `createImageRecoveryProvider` can use the same port for actual FAT32/exFAT regular-image analysis and allocated-file export, with physical execution still disabled. See [the real exFAT module](exfat-recovery.md). NTFS file-record analysis and physical acquisition remain unsupported. A future reviewed hardware adapter must supply actual parser evidence, helper-owned source identity/handles, verified separate destination topology, bounded I/O, cancellation, hashes and audit metadata; the current factory rejects physical-execution adapters. A model name or synthetic record cannot enable a production capability.

Tests cover both synthetic filesystems, acquisition/recovery simulation, unchanged source digests, explicit provenance, private path omission, separate/exclusive outputs, cancellation, fixture mutation and production refusal. They operate only on disposable regular files.
