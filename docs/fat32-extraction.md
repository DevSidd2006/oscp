# Bounded allocated FAT32 file extraction

The production UI requires review of the selected image, partition, candidate and logical byte size, plus explicit acknowledgement that this exports an allocated file rather than recovering deleted data. Only then does the native destination picker open. A new filename on separate physical storage is required. Cancelling or dismissing confirmation performs no extraction. Changing partition or refreshing inventory clears the prior acknowledgement. Progress, cancellation, verification hashes, retained partial output and failed/uncertain results are reported from the actual extraction service, not simulated values.

This milestone exports the logical bytes referenced by an **allocated regular file in a FAT32 root directory** from a selected regular raw image to a new output file on separately resolved physical storage. It is not deleted-file recovery, physical acquisition, filesystem repair, or NTFS/exFAT extraction. Deleted entries, directories, uncertain candidate metadata, files above 64 MiB and chains above 16384 clusters are refused.

The engine re-inventories the root, revalidates boot geometry, checks the relevant allocation-table mirrors or selected active FAT, and preflights the complete file chain before creating output. Free, bad, reserved, out-of-volume, repeated and root-directory-overlapping clusters are refused. Chain length must match the stored file size exactly. Only logical file bytes are exported; final-cluster slack is excluded. Empty allocated files with zero first cluster are supported. Long filenames, subdirectories and file contents beyond the selected allocated record are not analyzed.

`fat32-extraction-service.ts` obtains source paths from a validated main-process selected-image snapshot and output paths from a native save-dialog callback. Renderer inputs identify only an image token, partition index and record ID. The service opens the image read-only and compares its held-handle and visible-path device, inode, size, modification and change-time identity before and after every bounded source read. It requires independently helper-resolved source and destination physical identities with no overlap, known free capacity including a metadata reserve, and repeated identity checks before and after exclusive output creation and before successful completion. The helper's supported-topology restrictions still apply. These checks are snapshots, not protection against arbitrary privileged manipulation of Windows topology.

Outputs and `.oscp.json` sidecars use exclusive creation. Existing output or sidecar files and audit directories are refused. The service streams bounded reads and writes, flushes output, re-reads it to compute an output SHA-256 and compares it with the source-content stream digest. It verifies output identity, closes source/output handles, persists metadata and records an audit completion before publishing `completed`. An audit or final metadata error prevents a completed result. Cancellation, failures and uncertain verification retain files already created and record explicit states; retained data must not be mistaken for a completed export. Cancellation is cooperative between I/O operations.

The metadata contains the operation scope, tool version, source file identity and physical IDs, destination IDs, candidate, timestamps, byte counts, hashes, result/error and limitations. A matching content hash verifies the observed export bytes, not the original image's acquisition completeness, physical-media readback, complete filesystem consistency or allocation ownership against every other file chain. FAT metadata can be corrupt or cross-linked; this bounded extractor performs the stated checks and makes no broader authenticity claim.

The format semantics follow the Microsoft FAT specification referenced in [file-record-analysis.md](file-record-analysis.md). Tests use disposable sparse regular images and injected destination identity resolvers; they do not constitute real separate-device validation. They verify a fragmented file's exact output, empty files, chain failures, deleted/directory refusal, source-image SHA-256 preservation, same-disk/capacity/topology gates, no overwrite, cancellation, output hashes, audit failures and shutdown. Production wiring must continue using the trusted Windows helper resolver rather than the fixture IDs.
