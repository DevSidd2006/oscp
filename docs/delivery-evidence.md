# Delivery prerequisite checks and evidence

The dashboard's **Package and WinPE checks** panel performs read-only local checks. **Check delivery prerequisites** inspects built renderer/main/preload files, the expected helper assembly, whether Electron reports a packaged runtime, and the default Windows ADK/WinPE `copype.cmd` and `oscdimg.exe` paths. It never executes a discovered tool, builds an installer, assembles a boot image or writes removable media.

Each check is `present`, `missing`, `invalid` or `unverified`. Resource presence means a nonempty regular file exists at the expected path. A manifest is present only when bounded JSON parsing establishes a package name and version matching the running application; the expected `dist/main/main.js` entry point is checked separately. Malformed, oversized, changed or mismatched manifests are invalid. I/O failures that prevent inspection are unverified. No manifest script is run and no declared entry-point or resource path is followed.

The checker reads at most 1 MiB plus one byte from the fixed application `package.json`, verifies held-file identity/size/timestamps, and checks renderer/main/preload plus helper assembly, dependency manifest and runtime configuration files. Missing dependencies remain visible. Helper files do not prove the .NET runtime exists or the helper can launch on a clean system. Inline builder rules, when present, are observations only; external/default packaging configuration and actual artifact contents require separate validation.

Presence does not establish executable provenance, compatible versions, signing, licensing or successful operation. Custom ADK locations are not discovered. Non-Windows environments report tooling as unverified. A packaged runtime is an observation, not a clean-install result. The UI displays counts for each state and labels these checks as safe mode.

**Save release evidence** runs fresh checks and writes an unsigned JSON snapshot through the main-process native Save dialog. Choose a new filename: exclusive creation refuses to replace any existing file, including an earlier evidence report. Cancelling creates no report. A save error must not be treated as captured evidence. Reports include application version, capture time, platform, packaged state, check results and limitations; they do not include raw storage contents or execute external programs.

The snapshot intentionally records installer artifact/checksums, Authenticode signature/trust, clean install/upgrade/uninstall, installed-helper workflows, WinPE boot/driver validation and boot-media target safety as **unverified**. Unverified signing does not mean unsigned; no signature verifier was run. It cannot attest to work it did not perform. Record those results separately with artifact hashes/signing status, supported Windows/firmware versions, test procedures, observed output and failure cases. See [workflow acceptance](workflow-acceptance.md) and [implementation status](implementation-status.md).

Both `installerEnabled` and `winpeEnabled` are always false. Even a snapshot with all local prerequisites present cannot enable these operations. The UI has disabled installer and WinPE actions; export and checks are the only enabled delivery functions. No status field is an authorization token.

`tests/unit/delivery-readiness.test.ts` uses temporary synthetic build/tool files to verify that presence never becomes release authorization, malformed/oversized/mismatched manifests are refused, missing/non-Windows prerequisites are reported honestly, and fresh evidence creation refuses overwrite (including an existing package manifest). `tests/desktop/report-smoke.cjs` exercises safe-mode UI counts, invalid manifest/unverified signature and clean-install states, disabled installer/WinPE actions, and evidence cancellation/success through the sandboxed preload. These tests validate the checker and report boundary, not a real installer or boot image. No installer was run for these checks.
